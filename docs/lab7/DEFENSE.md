## 1. Теория простыми словами (Без абстрактных метафор)

### 1.1. "Толстый" vs "Тонкий" клиент

Любая веб-система состоит из двух частей:
1. **Клиент** — программа на устройстве пользователя (в нашем случае это веб-браузер Google Chrome, Firefox и т.д.).
2. **Сервер** — программа на удаленном компьютере, которая хранит базу данных и обрабатывает бизнес-правила (в нашем случае это Spring Boot на Java).

Разница между «тонким» и «толстым» клиентом заключается в том, **где именно выполняется логика построения внешнего вида страницы и обработка действий пользователя**.

#### Тонкий клиент (Server-Side Rendering, SSR)
- **Как работает**: Пользователь нажимает кнопку. Браузер отправляет запрос на сервер. Сервер на Java (например, через шаблонизатор Thymeleaf или JSP) считывает данные из БД, сам склеивает готовый HTML-документ со всеми стилями и отправляет его обратно браузеру. Браузер просто отображает готовый HTML.
- **Минусы**: При каждом переходе или клике страница в браузере полностью перезагружается (появляется белый экран на долю секунды). Сервер тратит много процессора и памяти на генерацию HTML для каждого пользователя.

#### Толстый клиент (Single Page Application, SPA)
- **Как работает**: Пользователь один раз открывает сайт. Сервер отдает ему один пустой HTML-каркас и программу на JavaScript/TypeScript (наш React-бандл). Дальше вся работа происходит внутри браузера:
  - Программа на React сама создает кнопки, карточки, таблицы и формы.
  - Сама проверяет, заполнил ли пользователь поле «Название».
  - Переключает экраны без единой перезагрузки страницы.
  - А к серверу обращается только тогда, когда нужны «сырые» данные (отправляет и получает компактный JSON через REST API).
- **Наш выбор**: Наше приложение — это **толстый клиент** на React + TypeScript. Сервер Spring Boot занимается только данными и бизнес-логикой, а браузер занимается логикой отображения.

### 1.2. Что такое SPA (Single Page Application)

**SPA (Одностраничное приложение)** — это веб-сайт, который загружает в браузер ровно **одну** HTML-страницу (`index.html`). 

- **Как это работает в коде**:
  - В файле [`frontend/index.html`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/index.html) есть единственный корневой блок: `<div id="root"></div>`.
  - В файле [`frontend/src/main.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/main.tsx) библиотека React подключается к этому блоку: `ReactDOM.createRoot(document.getElementById('root')!).render(<App />)`.
  - Когда пользователь переключает табы («Рецепты», «Фильтрация», «Многопоточность») в компоненте [`frontend/src/Navbar.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/Navbar.tsx), браузер **не** делает запрос к серверу за новым файлом страницы. Вместо этого меняется переменная состояния `activeTab` в памяти JavaScript (`useState`), и React мгновенно заменяет видимые элементы на экране. Страница не мигает, пользовательский опыт сравним с обычным приложением на смартфоне или компьютере.

### 1.3. Отображение связей реляционной базы данных (OneToMany и ManyToMany)

В реляционной базе данных PostgreSQL таблицы связаны внешними ключами. В SPA-клиенте эти связи визуализированы наглядно:

#### 1. Связь OneToMany («Один ко многим»)
- **В базе данных**: Один рецепт содержит много шагов приготовления. В таблице `cooking_steps` есть колонка `recipe_id`, указывающая на родительский рецепт `recipes.id`.
- **В JSON от бэкенда**: Объект рецепта содержит список объектов шагов:
  ```json
  "steps": [
    { "stepOrder": 1, "description": "Помыть овощи" },
    { "stepOrder": 2, "description": "Нарезать кубиками" }
  ]
  ```
- **В интерфейсе клиента**:
  - В компоненте [`RecipeModal.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/RecipeModal.tsx) шаги отображаются в виде упорядоченной последовательности блоков с номерами шагов (`stepOrder`).
  - В форме [`RecipeFormModal.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/RecipeFormModal.tsx) пользователь может динамически добавлять новые шаги, удалять ненужные и перемещать их вверх/вниз стрелками.

#### 2. Связь ManyToMany («Многие ко многим»)
- **В базе данных**: Один рецепт может содержать много ингредиентов, и один и тот же ингредиент (например, «Соль» или «Картофель») может использоваться во множестве разных рецептов. В БД это реализовано через связующую таблицу `recipe_ingredients(recipe_id, ingredient_id)`.
- **В JSON от бэкенда**: Рецепт возвращает список связанных ингредиентов:
  ```json
  "ingredients": [
    { "id": 1, "name": "Картофель" },
    { "id": 4, "name": "Морковь" }
  ]
  ```
- **В интерфейсе клиента**:
  - В карточке [`RecipeCard.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/RecipeCard.tsx) и деталях [`RecipeModal.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/RecipeModal.tsx) ингредиенты выводятся в виде интерактивных «чипсов» (бейджей).
  - В форме создания [`RecipeFormModal.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/RecipeFormModal.tsx) реализован мультиселект: клик по ингредиенту добавляет или убирает его ID из массива `selectedIngredientIds`, отправляемого на бэкенд.

### 1.4. Адаптивная вёрстка (Responsive Web Design)

**Адаптивная верстка** — это подход к созданию интерфейса, при котором сайт одинаково удобно читается и управляется как на узком экране смартфона (360px), так и на широком мониторе компьютера (1920px).

Ключевые инструменты, примененные в нашем проекте:
1. **Мета-тег Viewport**:
   В [`frontend/index.html`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/index.html):
   ```html
   <meta name="viewport" content="width=device-width, initial-scale=1.0" />
   ```
   *Зачем нужен*: Без этого тега мобильный браузер считает, что страница создана для экрана 980px, и принудительно уменьшает весь масштаб сайта, превращая текст в микроскопический. Тег указывает браузеру масштабировать страницу 1:1 в соответствии с физической шириной устройства.

2. **Tailwind CSS Breakpoints (Медиа-запросы)**:
   Мы используем классы с префиксами контрольных точек:
   - `sm:` — экраны от 640px (планшеты).
   - `md:` — экраны от 768px (ноутбуки).
   - `lg:` — экраны от 1024px (широкие мониторы).
   *Пример из `RecipeCard` и `App.tsx`*:
   `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3` означает: на телефоне карточки выстраиваются в 1 колонку, на планшете в 2 колонки, на компьютере в 3 колонки.

3. **Mobile-First**:
   Сначала задаются стили для самого узкого экрана мобильного телефона, а затем с помощью `sm:` и `md:` добавляются расширенные правила для больших мониторов.

### 1.5. Принципы UI/UX

- **UI (User Interface)** — то, **как выглядит** система: цвета, шрифты, отступы, иконки, контрастность кнопок.
- **UX (User Experience)** — то, **как система работает и ощущается пользователем**: насколько легко выполнить задачу, не запутан ли сценарий, понятно ли, что происходит прямо сейчас.

Примененные принципы:
1. **Правило обратной связи (Feedback)**:
   Пользователь никогда не должен гадать, завис сайт или работает.
   - Во время выполнения запроса на кнопках появляется крутящийся индикатор (`Loader2 animate-spin`) и текст меняется на «Сохранение...» или «Поиск...».
   - При расчете КБЖУ в Лабе 6 отображается статус фоновой задачи: «Запрос отправлен в пул потоков...».
2. **Защита от ошибочных действий (Error Prevention)**:
   - Кнопка «Удалить» рецепт или категорию не удаляет запись молча, а запрашивает подтверждение через диалоговое окно `confirm(...)`.
   - В формах заблокирована отправка с пустыми полями (клиентская валидация).
3. **Закон Фиттса**:
   Кнопки основных действий («Создать рецепт», «Поиск», «Закрыть») сделаны крупными и расположены в зонах легкого клика и тапа пальцем.
4. **Визуальная иерархия**:
   Главный заголовок — крупный и жирный, второстепенный текст — серый и меньшего размера, технические ID — мелким моноширинным шрифтом.

### 1.6. SEO и PWA

#### SEO (Search Engine Optimization, Поисковая оптимизация)
- **Проблема у SPA**: Поисковые роботы (например, Яндекс или Google) запрашивают страницу по URL. В обычном SPA бэкенд возвращает только пустой HTML `<div id="root"></div>` и ссылку на скрипт. Некоторые роботы не ждут выполнения тяжелого JavaScript и индексируют пустую страницу.
- **Решение проблемы**:
  - **SSR (Server-Side Rendering)**: Сервер на Node.js (например, Next.js) перед отправкой страницы выполняет React-код и присылает роботу уже наполненный текстом HTML.
  - **SSG (Static Site Generation)**: Все страницы генерируются в готовые HTML-файлы еще на этапе сборки проекта.

#### PWA (Progressive Web App)
**PWA** — это веб-сайт, обладающий возможностями мобильного приложения:
- Его можно «установить» на рабочий стол смартфона в виде отдельной иконки без App Store / Google Play.
- Он может работать офлайн (без интернета) благодаря фоновому скрипту **Service Worker**, кэширующему страницы и запросы.
- Он может присылать Push-уведомления пользователю.

## 2. Ловушки преподавателя и каверзные вопросы (Q&A)

### Вопрос 1 (Главная ловушка по архитектуре):
> *«Почему вы сделали толстый клиент (SPA на React), а не использовали серверный рендеринг (Thymeleaf)? В каких случаях Thymeleaf был бы более правильным выбором?»*

**Правильный ответ**:
1. Мы выбрали SPA на React, потому что требовалось построить высокоинтерактивный пользовательский интерфейс с моментальной фильтрацией, всплывающими окнами, динамическим добавлением шагов и постоянным мониторингом многопоточных счетчиков без перезагрузки страниц.
2. Кроме того, SPA полностью отделяет фронтенд от бэкенда: бэкенд предоставляет универсальный REST API по протоколу HTTP/JSON, к которому в будущем можно подключить не только веб-браузер, но и мобильное приложение для iOS/Android или сторонние сервисы.
3. **Когда Thymeleaf был бы лучше**: Thymeleaf идеален для простых контентных сайтов (блоги, каталоги статей, корпоративные страницы), где критически важна быстрая индексация поисковиками (SEO «из коробки») и где нет сложного клиентского состояния (state), а также для небольших внутренних панелей администрирования, чтобы не подключать Node.js и сложные сборщики.

### Вопрос 2 (Ловушка по сетевой безопасности):
> *«Что такое CORS? Почему при запуске Vite на порту 5173 ваши запросы к порту 8080 были бы заблокированы браузером, если бы мы не добавили `WebConfig`?»*

**Правильный ответ**:
1. **CORS (Cross-Origin Resource Sharing)** — это защитный механизм, встроенный в браузер.
2. По правилу **Same-Origin Policy** браузер разрешает JavaScript-коду делать запросы только к тому же протоколу, домену и порту, с которого была загружена сама страница.
3. Страница загружается с `http://localhost:5173`, а Spring Boot слушает на `http://localhost:8080`. Порты разные — значит это Cross-Origin запрос.
4. Перед выполнением модифицирующих запросов браузер отправляет так называемый предварительный запрос (Preflight Request методом `OPTIONS`). Если сервер не пришлет в заголовке `Access-Control-Allow-Origin: http://localhost:5173`, браузер заблокирует чтение ответа в JavaScript.
5. Мы решили это в коде: на бэкенде создан класс [`WebConfig.java`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/config/WebConfig.java), где через `registry.addMapping("/api/**").allowedOriginPatterns(...)` мы явно разрешили локальные запросы от сервера разработки. А в файле [`vite.config.ts`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/vite.config.ts) мы настроили внутреннее проксирование запросов к порту 8080.

### Вопрос 3 (Ловушка по валидации):
> *«У вас валидация полей реализована в форме на клиенте в `RecipeFormModal.tsx`. Значит ли это, что валидацию на бэкенде через аннотации `@NotBlank` и `@NotNull` можно удалить?»*

**Правильный ответ**:
**Ни в коем случае!** Клиентская валидация делается **исключительно для удобства пользователя (UX)**, чтобы мгновенно подсказать ему об ошибке без задержки на сетевой запрос.
Любой злоумышленник или тестировщик может обойти фронтенд (отправив запрос через curl, Postman или изменив код в консоли браузера). **Единственным гарантом целостности данных является серверная валидация** (`@Valid`, `@NotBlank`, `@NotNull` в Spring DTO). Сервер обязан всегда перепроверять входные данные независимо от того, что делает клиент.

### Вопрос 4 (Ловушка по безопасности React):
> *«Как React защищает пользователя от XSS-атак (внедрения вредоносного JavaScript-кода в описание рецепта)?»*

**Правильный ответ**:
По умолчанию React автоматически экранирует (escapes) любые строки, вставляемые через фигурные скобки `{recipe.description}` в JSX. Если злоумышленник сохранит в названии рецепта строку `<script>alert('взлом')</script>`, React отрендерит это не как исполняемый тег скрипта в DOM, а как безопасный текстовый узел (эквивалентно HTML-сущностям `&lt;script&gt;`). Единственный способ случайно разрешить XSS в React — это явно использовать опасное свойство `dangerouslySetInnerHTML`, чего в нашем проекте нет.

4. В табе «Многопоточность» в компоненте [`ConcurrencySection.tsx`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/frontend/src/components/ConcurrencySection.tsx) пользователь может нажать «Запустить атаку гонки».
