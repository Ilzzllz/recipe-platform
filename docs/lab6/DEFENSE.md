## Тема 1. Потоки и процессы в операционной системе и Java

### Что такое процесс (Process)?
**Процесс** — это работающая программа в операционной системе (например, запущенная виртуальная машина Java `java.exe`).
- У каждого процесса есть **собственное изолированное адресное пространство памяти**, свои системные дескрипторы файлов и сетевые порты.
- Один процесс не может напрямую прочитать память другого процесса — для их общения требуется межпроцессное взаимодействие (IPC — сокеты, файлы, пайпы).

### Что такое поток (Thread)?
**Поток (нить исполнения)** — это наименьшая единица работы внутри процесса, которой операционная система выделяет процессорное время.
- Внутри одного процесса (одной JVM) может работать множество потоков.
- **Общая память (Heap / Куча)**: все потоки одного процесса делят между собой общие объекты в куче. Если один поток изменил поле объекта, другие потоки могут увидеть это изменение.
- **Собственная память потока (Thread Stack / Стек вызовов)**: у каждого потока есть свой приватный стек, где хранятся локальные переменные методов и цепочка вызовов. Локальные переменные одного потока недоступны другим потокам.

| Характеристика | Процесс (Process) | Поток (Thread) |
| :--- | :--- | :--- |
| **Память** | Изолированная у каждого процесса. | Общая память кучи (Heap) на все потоки процесса. |
| **Ресурсы на создание** | "Тяжелый": требует выделения памяти ОС, таблиц страниц. | "Легкий": выделяется только стек (по умолчанию 1 МБ). |
| **Переключение контекста** | Медленное (сброс кэшей процессора, смена адресного пространства). | Быстрое (сохраняются только регистры и указатель стека). |

## Тема 2. Проблемы многопоточности: Race Condition и Deadlock

### 1. Состояние гонки (Race Condition)
**Состояние гонки** — это ошибка многопоточного кода, при которой результат выполнения программы зависит от того, в каком непредсказуемом порядке операционная система переключала потоки на процессоре.

#### Как возникает потеря обновления (Lost Update) на операции `count++`?
Операция инкремента `count++` на самом деле состоит из **трех отдельных микро-инструкций**:
1. **READ**: прочитать значение переменной из оперативной памяти в регистр процессора (например, прочитали `5`).
2. **MODIFY**: увеличить значение в регистре на 1 (`5 + 1 = 6`).
3. **WRITE**: записать новое значение из регистра обратно в оперативную память.

Если два потока (Поток А и Поток Б) одновременно выполняют инкремент:
1. Поток А читает `5`.
2. ОС прерывает Поток А и переключает на Поток Б.
3. Поток Б тоже читает `5` из памяти.
4. Поток Б увеличивает до `6` и записывает `6` в память.
5. ОС возвращает управление Потоку А. Поток А помнит, что прочитал `5`, увеличивает до `6` и записывает `6` в память.
6. **Итог**: два потока выполнили по инкременту, но значение увеличилось только на 1 вместо 2. Одно обновление потеряно!

В нашем проекте класс [`RecipeViewCounterService`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/service/RecipeViewCounterService.java) наглядно демонстрирует эту проблему в переменной `unsafeCounter++`.

### 2. Взаимная блокировка (Deadlock)
**Взаимная блокировка (Deadlock)** — ситуация, когда два или более потоков бесконечно ждут освобождения ресурсов, удерживаемых друг другом.

**Классический пример**:
- Поток 1 захватил Ресурс А и пытается захватить Ресурс Б.
- Поток 2 в это же время захватил Ресурс Б и пытается захватить Ресурс А.
- Ни один поток не может продолжить работу, программа "зависает" навсегда.

#### 4 обязательных условия возникновения Deadlock (условия Коффмана):
1. **Взаимное исключение**: ресурс может использоваться только одним потоком единовременно.
2. **Удержание и ожидание**: поток держит один ресурс и одновременно ждет другой.
3. **Отсутствие вытеснения**: ресурс нельзя отобрать силой, пока поток сам его не отпустит.
4. **Круговое ожидание**: существует замкнутая цепь потоков, каждый из которых ждет ресурс следующего.

**Как бороться с Deadlock?**
- Главное правило: **фиксированный глобальный порядок блокировок**. Все потоки должны захватывать ресурсы строго в одинаковой последовательности (например, сначала Ресурс А, затем Ресурс Б).
- Использовать `tryLock(timeout)` из интерфейса `Lock` вместо жесткого `synchronized`: если замок не получен за отведенное время, поток отпускает свои ресурсы и пробует позже.

## Тема 3. Способы создания потоков в Java и пулы потоков (ExecutorService)

### Способы создания потока в Java

1. **Наследование от класса `Thread`**:
   ```java
   class MyThread extends Thread {
       @Override
       public void run() { }
   }
   new MyThread().start();
   ```
   *Минус*: Java не поддерживает множественное наследование классов, класс больше ни от чего не сможет наследоваться.
2. **Реализация интерфейса `Runnable`**:
   ```java
   Runnable task = () -> System.out.println("Работа в потоке");
   new Thread(task).start();
   ```
   *Плюс*: разделение задачи (`Runnable`) и механизма ее запуска (`Thread`).
   *Минус*: метод `run()` не может вернуть результат и не может выбросить checked-исключение.
3. **Интерфейс `Callable<V>` и `Future<V>`**:
   ```java
   Callable<String> task = () -> "Результат";
   ```
   *Плюс*: метод `call()` возвращает значение и может выбрасывать исключения.

---

### Почему в продакшене нельзя писать `new Thread().start()`?
Создание потока операционной системы — дорогая операция (выделяется 1 МБ памяти под стек, задействуется ядро ОС). Если придет 10 000 HTTP-запросов и мы создадим 10 000 потоков, сервер упадет с ошибкой `OutOfMemoryError: unable to create new native thread`.

Вместо этого используют **Пулы потоков (Thread Pools)** через интерфейс **`ExecutorService`**.

### Архитектура пула потоков (`ThreadPoolExecutor`)
Пул создает фиксированное количество рабочих потоков заранее и держит очередь задач:
- **`corePoolSize`**: количество постоянных потоков, готовых к работе.
- **`queueCapacity`**: очередь входящих задач. Если все базовые потоки заняты, новые задачи встают в очередь.
- **`maxPoolSize`**: максимальный размер пула. Если очередь переполнена, пул создает дополнительные потоки вплоть до этого лимита.
- **`RejectedExecutionHandler`**: политика отказа, если очередь полна и лимит потоков исчерпан (например, выбросить ошибку или выполнить задачу в потоке вызывающего).

В нашем проекте пул настроен в классе [`AsyncConfig.java`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/config/AsyncConfig.java).

## Тема 4. Модель памяти Java (JMM): volatile, synchronized и Atomic

### 1. Ключевое слово `volatile`
- **Проблема**: Для ускорения работы современные процессоры кэшируют переменные в сверхбыстрой кэш-памяти ядер (L1/L2/L3). Если поток на Ядре 1 изменил переменную, Ядро 2 может долго не видеть этого изменения, читая свое старое значение из кэша.
- **Что делает `volatile`**:
  - Гарантирует **видимость (Visibility)**: чтение переменной всегда происходит напрямую из оперативной памяти (RAM), а запись немедленно сбрасывается в RAM.
  - Запрещает переупорядочивание инструкций компилятором (Happens-Before).
- **Чего НЕ делает `volatile`**:
  - `volatile` **НЕ делает операцию `count++` атомарной!** Операция чтения и записи все равно остаются разделенными во времени, поэтому гонка потоков не устраняется.

---

### 2. Ключевое слово `synchronized`
- **Что делает**:
  - Обеспечивает **взаимное исключение (Mutual Exclusion)**: одновременно только один поток может выполнять блок или метод, помеченный `synchronized`.
  - Каждый объект в Java имеет встроенный скрытый замок — **Монитор (Monitor / Intrinsic Lock)**. Поток при входе захватывает монитор, а при выходе освобождает его.
  - Автоматически гарантирует видимость изменений памяти (при выходе из монитора все кэши сбрасываются в RAM).
- **Минус**: блокировка потоков переводит их в состояние ожидания (BLOCKED), что вызывает накладные расходы операционной системы на переключение контекста.

---

### 3. Классы пакета `java.util.concurrent.atomic` (AtomicLong, AtomicInteger)
- **Как работают**:
  - Обеспечивают потокобезопасность **без блокировок (Lock-Free)**. Потоки не засыпают и не блокируются.
  - Используют низкоуровневую процессорную инструкцию **CAS (Compare-And-Swap — Сравнить и Заменить)**.
  - **Алгоритм CAS**: процессор атомарно на уровне микрокода проверяет: *"Если значение в ячейке памяти все еще равно X, то запиши туда Y. Если значение уже изменил другой поток, не меняй ничего и сообщи о неудаче"*. При неудаче поток просто пробует снова в цикле.
- **В нашем проекте**:
  [`RecipeViewCounterService`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/service/RecipeViewCounterService.java) использует `AtomicLong` для подсчета просмотров:
  ```java
  private final AtomicLong atomicCounter = new AtomicLong(0);
  atomicCounter.incrementAndGet(); // Атомарно и без блокировок!
  ```

## Тема 5. Асинхронное программирование: CompletableFuture и @Async

### Зачем нужна асинхронность в Web-приложениях?
Веб-сервер (Tomcat) выделяет один поток на обработку одного входящего HTTP-запроса. Если сервер делает долгий сетевой запрос (например, опрос внешнего сервиса на 3 секунды), этот поток блокируется и простаивает. Если придет 200 одновременных запросов, пул потоков Tomcat исчерпается, и сайт перестанет отвечать новым пользователям.

### Как работает `@Async` в Spring?
1. Мы помечаем конфигурацию аннотацией `@EnableAsync`.
2. Метод сервиса помечается `@Async("имяПула")` и возвращает `CompletableFuture<T>`.
3. При вызове метода Spring с помощью паттерна **Proxy** перехватывает вызов, упаковывает выполнение метода в задачу и отправляет ее в указанный пул потоков (`recipeTaskExecutor`).
4. Метод контроллера моментально получает объект `CompletableFuture` и может сразу вернуть ответ клиенту (например, HTTP 202 Accepted с ID задачи), а фоновый поток продолжает работать.

---
 
### Класс `CompletableFuture<T>`
`CompletableFuture` (появился в Java 8) — это расширенный `Future`, который позволяет строить асинхронные конвейеры в функциональном стиле без блокирующего вызова `.get()`:
- `thenApply(Function)` — преобразовать результат, когда он будет готов;
- `thenCompose(Function)` — запустить следующую асинхронную задачу по готовности первой;
- `thenCombine(...)` — дождаться завершения двух параллельных задач и объединить их результаты;
- `CompletableFuture.allOf(f1, f2, f3)` — дождаться завершения целого массива параллельных задач.

## Тема 6. Нагрузочное тестирование и основы Apache JMeter

### Что такое нагрузочное тестирование?
**Нагрузочное тестирование** — это проверка поведения и производительности системы при одновременной работе большого количества пользователей.

### Главные метрики нагрузочного тестирования:
1. **RPS / Throughput (Запросов в секунду)**: сколько HTTP-запросов сервер успевает успешно обработать за одну секунду.
2. **Response Time / Latency (Время ответа)**: сколько миллисекунд проходит от отправки запроса до получения ответа.
3. **Процентили (Percentiles: 95th, 99th)**:
   - Среднее время ответа часто обманчиво.
   - 95-й процентиль (p95) означает, что 95% пользователей получили ответ быстрее этого времени, и только 5% ждали дольше.
4. **Error Rate (Процент ошибок)**: процент запросов, завершившихся с кодом 5xx или тайм-аутом. В здоровой системе должен быть 0.00%.

### Устройство Apache JMeter:
- **Thread Group (Группа потоков)**: эмулирует пользователей (указывается количество виртуальных пользователей, время разгона `Ramp-up` и количество повторений `Loop Count`).
- **HTTP Request Sampler**: задает целевой хост, порт, метод (`GET`) и путь (`/api/recipes/1`).
- **Listeners (Слушатели)**: компоненты визуализации (`Summary Report`, `View Results Tree`), показывающие время отклика, графики и статистику ошибок.

## Тема 7. Защита и мониторинг высоконагруженных систем: RateLimiter и ELK-стек

### 1. Паттерн RateLimiter (Ограничитель частоты запросов)
**RateLimiter** — это механизм, который ограничивает количество запросов, разрешенных клиенту за определенный интервал времени (например, не более 10 запросов в секунду от одного IP).
- **Зачем нужен**:
  - Защита от DoS-атак и злоупотреблений;
  - Защита базы данных от перегрузки (Backpressure);
  - Монетизация API (ограничение по тарифным планам).
- **Алгоритмы**:
  - **Token Bucket (Корзина токенов)**: в корзину с постоянной скоростью капают токены. Каждый запрос забирает токен. Если токенов нет — запрос отклоняется (HTTP 429 Too Many Requests).
  - **Leaky Bucket (Дырявое ведро)**: сглаживает пики нагрузки, обрабатывая запросы с фиксированной скоростью.

---

### 2. Стек ELK (Elasticsearch, Logstash, Kibana)
В современных микросервисах логи не смотрят вручную в текстовых файлах на серверах. Для этого используется **ELK-стек**:
1. **Logstash (или Filebeat)**: агент-сборщик, который читает файлы логов со всех серверов, парсит строки и отправляет их в единую базу.
2. **Elasticsearch**: распределенная документоориентированная поисковая система. Хранит терабайты логов и позволяет искать по ним со скоростью миллисекунд.
3. **Kibana**: красивый веб-интерфейс, где разработчики и администраторы строят графики ошибок, анализируют всплески нагрузки и просматривают стек-трейсы сбоев в реальном времени.

## Блок: Каверзные вопросы и ловушки преподавателя с готовыми ответами

### Вопрос 1: Почему переменная `volatile int counter` не спасает от состояния гонки при инкременте `counter++`?
**Ответ:**
Ключевое слово `volatile` гарантирует только видимость (чтение из оперативной памяти, а не из локального кэша процессора). Но операция `counter++` состоит из трех отдельных действий: чтение, увеличение значения и запись обратно. `volatile` не делает эти три действия неделимыми. Если два потока прочитают старое значение одновременно, они оба запишут одинаковый результат, и одно обновление будет потеряно. Для атомарности нужен `AtomicInteger` или блок `synchronized`.

---

### Вопрос 2: Как устроен алгоритм CAS (Compare-And-Swap) внутри `AtomicLong`?
**Ответ:**
CAS работает без захвата блокировок ОС. Процессор выполняет специальную неделимую инструкцию: он сравнивает текущее значение переменной в памяти с тем значением, которое поток прочитал до вычисления. Если значение не изменилось, процессор записывает новый результат. Если значение уже изменилось другим потоком, CAS сообщает о неудаче, и поток в цикле повторяет чтение и попытку записи заново.

---

### Вопрос 3: Что произойдет, если в методе с аннотацией `@Async` вызвать другой метод с аннотацией `@Async` того же самого класса (`self-invocation`)?
**Ответ:**
Асинхронный запуск **НЕ произойдет** — второй метод выполнится синхронно в том же самом потоке!
Spring реализует `@Async` через создание **динамического Proxy-объекта**. Когда вызов идет из другого бина, он проходит через Proxy, который и перенаправляет задачу в пул потоков. Но при вызове внутри того же класса через `this.method()` обращение идет напрямую к реальному объекту в обход Spring Proxy.

---

### Вопрос 4: Как клиент понимает, завершилась ли асинхронная задача, запущенная через `POST /api/recipes/{id}/nutrition-report`?
**Ответ:**
Эндпоинт запуска сразу возвращает статус `202 Accepted` и уникальный `taskId` (UUID). Клиент сохраняет этот ID и периодически отправляет опрашивающий запрос `GET /api/recipes/nutrition-report/{taskId}` (паттерн **Polling**). Пока задача выполняется, сервер возвращает статус `IN_PROGRESS`. Как только фоновый расчет завершен, статус меняется на `COMPLETED`, и в теле ответа появляется готовый блок данных `result` с расчетом КБЖУ.

### Вопрос 5: Что произойдет, если в пуле `ThreadPoolTaskExecutor` закончатся свободные потоки и переполнится очередь задач?
**Ответ:**
Сработает механизм отказа (**RejectedExecutionHandler**). По умолчанию в Spring Boot используется политика `AbortPolicy`, которая выбрасывает исключение `TaskRejectedException`, а клиент получит ошибку 500 (или 429 при настроенном обработчике). Другие политики позволяют, например, выполнить задачу прямо в потоке вызывающего (`CallerRunsPolicy`) или молча отбросить задачу (`DiscardPolicy`).

### Вопрос 6: В чем разница между `CountDownLatch` и `CyclicBarrier`?
**Ответ:**
- **`CountDownLatch`** — это одноразовый счетчик. Потоки ждут, пока счетчик не уменьшится до 0 вызовами `countDown()`. После этого защелка открывается навсегда и повторно использована быть не может (мы использовали ее для одновременного старта 50 потоков в тесте Race Condition).
- **`CyclicBarrier`** — это многоразовый барьер, который ждет, пока N потоков соберутся в одной точке (вызовут `await()`), после чего все вместе продолжают движение, а барьер автоматически сбрасывается для следующего цикла.

### Вопрос 7 (Ловушка преподавателя по внешнему API):
> *«Что произойдет, если пользователь опечатался в названии ингредиента (например, написал „морквь“ вместо „морковь“) или если внешний сервис Open Food Facts вернет пустой результат / будет недоступен?»*

**Ответ:**
1. **Что вернет внешний API**:
   Сервис Open Food Facts вернет обычный ответ `HTTP 200 OK`, но массив найденных товаров будет пустым: `{"products": []}`.
2. **Как это обрабатывает наш сервер**:
   В методе [`NutritionReportService.fetchIngredientNutrition()`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/service/NutritionReportService.java#L143) применен паттерн **Graceful Degradation (Мягкая деградация)**:
   - Программа проверяет: `if (products.isArray() && !products.isEmpty())`.
   - Если массив пуст (продукт не распознан из-за опечатки) или если отвалился интернет/выбросился сетевой таймаут, сервер **не падает с ошибкой 500 и не ломает фоновую задачу**.
   - Сервер автоматически возвращает стандартную базовую кулинарную оценку (45 ккал, 1.5 г белка, 0.5 г жира, 9.0 г углеводов) с явной пометкой источника данных: `"Standard culinary estimate"` (вместо `"Open Food Facts API"`).
3. **Итог**:
   Итоговый отчет все равно успешно рассчитывается со статусом `COMPLETED`, в таблице видно, какие ингредиенты были найдены во внешнем API, а для каких была использована стандартная оценка. Сервер работает максимально надежно и отказоустойчиво.
