## Тема 1. Пакетные (Bulk / Batch) операции

### Что такое Bulk-операция?
**Bulk-операция (пакетная операция)** — это обработка набора (списка) однотипных объектов за один входящий запрос к серверу.

### Зачем нужны пакетные операции?
1. **Экономия сетевых вызовов (Network Round-trips)**:
   Если клиенту нужно сохранить 100 рецептов, отправка 100 отдельных HTTP-запросов создаст огромную нагрузку на сеть. Пакетная операция отправляет все 100 объектов в одном HTTP-запросе.
2. **Атомарность бизнеса**:
   Часто набор данных имеет смысл только целиком (например, импорт кулинарной книги). Если на середине процесса произойдет сбой, база данных не должна остаться в испорченном, полупустом состоянии.

### Как транзакционность защищает Bulk-операцию?
- При наличии аннотации **`@Transactional`** все действия метода объединяются в единую неделимую транзакцию базы данных:
  - Если каждый объект пачки успешно сохранен — транзакция фиксируется (**Commit**), и все данные становятся видны в БД.
  - Если хотя бы один объект вызвал исключение (например, `NotFoundException`), транзакция откатывается (**Rollback**). Все предыдущие сохранения этой пачки отменяются, словно их никогда не было.
- **В нашем проекте**:
  - `POST /api/recipes/bulk` использует `@Transactional` — ошибка в конце отменяет все созданные ранее рецепты пачки.
  - `POST /api/recipes/bulk/no-tx` выполняется без общей транзакции — каждый рецепт сохраняется в БД по отдельности. При падении второго рецепта первый рецепт навсегда остается в базе данных.

## Тема 2. Java Stream API и лямбда-выражения

### Что такое лямбда-выражение?
**Лямбда-выражение** — это короткая запись анонимной функции, которую можно передать как параметр в другой метод или сохранить в переменную.

Синтаксис:
```java
(параметры) -> выражение
```
Например:
```java
id -> ingredientRepository.findById(id)
```
Лямбды в Java работают на базе **функциональных интерфейсов** — интерфейсов, которые содержат ровно один абстрактный метод (например, `Function<T, R>`, `Predicate<T>`, `Consumer<T>`, `Supplier<T>`).

### Что такое ссылка на метод (Method Reference)?
Это еще более короткая запись лямбды, если метод просто перенаправляет аргумент:
- Запись через лямбду: `recipe -> recipeMapper.toDto(recipe)`
- Запись через ссылку на метод: `recipeMapper::toDto`

---

### Что такое Stream API?
**Stream API** (появился в Java 8) — это инструмент для обработки последовательностей элементов в декларативном (функциональном) стиле. Поток (Stream) **не хранит** данные в памяти, а обрабатывает их на лету из источника (например, из списка).

### Конвейер стрима: промежуточные и терминальные операции
Любой стрим состоит из трех этапов:
1. **Источник** (создание стрима): `dtos.stream()`
2. **Промежуточные операции (Intermediate operations)**:
   - Преобразуют поток в другой поток.
   - Являются **ленивыми (lazy)**: они не начинают выполняться, пока не будет вызвана терминальная операция.
   - Примеры:
     - `map(...)` — преобразует каждый элемент одного типа в элемент другого типа (например, `RecipeCreateDto` в `Recipe`).
     - `filter(...)` — отбирает только элементы, удовлетворяющие условию.
     - `distinct()` — убирает дубликаты.
     - `sorted()` — сортирует элементы.
3. **Терминальные операции (Terminal operations)**:
   - Запускают фактическую обработку всех элементов по конвейеру и завершают работу стрима, возвращая конкретный результат.
   - Примеры:
     - `toList()` или `collect(Collectors.toList())` — собирает элементы в неизменяемый список.
     - `collect(Collectors.toSet())` — собирает элементы в множество без дубликатов.
     - `count()` — подсчитывает количество элементов.
     - `forEach(...)` — выполняет действие над каждым элементом.

### Где это в нашем коде:
В [`RecipeService.java`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/service/RecipeService.java):
```java
return dtos.stream()
        .map(this::convertToRecipe)          // промежуточная операция (преобразование)
        .map(recipeRepository::saveAndFlush) // промежуточная операция (сохранение в БД)
        .map(recipeMapper::toDto)            // промежуточная операция (преобразование в DTO)
        .toList();                           // терминальная операция (запуск и сборка в List)
```

## Тема 3. Класс Optional: борьба с NullPointerException

### Что такое Optional?
**`Optional<T>`** — это класс-обертка (контейнер), который может содержать значение типа `T`, либо быть пустым.

### Главная цель создания Optional
В старых версиях Java методы возвращали `null`, если объект не найден. Если программист забывал написать проверку `if (user != null)`, программа падала во время работы с ошибкой `NullPointerException` (NPE).
Класс `Optional` заставляет разработчика явно указать, что делать, если значение отсутствует.

### Ключевые методы Optional:
1. `Optional.empty()` — создает пустой контейнер.
2. `Optional.of(value)` — создает контейнер с ненулевым значением (выбросит ошибку, если передать `null`).
3. `Optional.ofNullable(value)` — создает контейнер, который может быть как со значением, так и пустым.
4. `isPresent()` — возвращает `true`, если внутри есть значение.
5. `isEmpty()` — возвращает `true`, если контейнер пуст.
6. `orElse(defaultValue)` — возвращает значение из контейнера, а если его нет — отдает запасное значение по умолчанию.
7. `orElseThrow(() -> new NotFoundException(...))` — возвращает значение, а если контейнер пуст — выбрасывает указанное исключение.

### Хороший и плохой стиль работы с Optional
- **Плохо (Антипаттерн)**:
  ```java
  Optional<User> opt = userRepository.findById(id);
  if (opt.isPresent()) {
      User user = opt.get(); // Вызов .get() вслепую опасен
  }
  ```
  Это ничем не отличается от старой проверки `if (user != null)`.
- **Хорошо (Как сделано в нашем проекте)**:
  ```java
  User author = userRepository.findById(dto.getAuthorId())
          .orElseThrow(() -> new NotFoundException("User with id " + dto.getAuthorId() + " was not found"));
  ```
  Код занимает одну строчку, читается как обычное английское предложение и гарантирует отсутствие непроверенных `null`.

## Тема 4. Пирамида тестирования и методология TDD

### Что такое пирамида тестирования?
**Пирамида тестирования** — это классическая модель, показывающая правильное соотношение разных видов автоматических тестов в проекте:

```
          / \
         /   \        UI / E2E тесты (Сквозные)
        /-----\       Мало, медленные, дорогие в поддержке
       /       \
      /---------\     Интеграционные тесты
     /           \    Среднее количество, проверяют работу с БД и HTTP
    /-------------\
   /               \  Модульные (Unit) тесты
  /-----------------\ Фундамент: ОЧЕНЬ МНОГО, выполняются мгновенно
```

1. **Основание — Unit-тесты (Модульные)**:
   - Тестируют один отдельный метод одного класса в полной изоляции.
   - Занимают 70-80% всех тестов проекта.
   - Выполняются за миллисекунды, потому что не запускают Spring и базу данных.
2. **Середина — Интеграционные тесты**:
   - Проверяют, как несколько компонентов работают вместе (например, сервис + реальный репозиторий + база данных PostgreSQL).
   - Выполняются дольше (секунды), так как поднимают соединения и пишут на диск.
3. **Вершина — E2E (End-to-End) тесты**:
   - Имитируют поведение реального пользователя через браузер или мобильное приложение.
   - Самые медленные и хрупкие к изменениям дизайна.

---

### Что такое TDD (Test-Driven Development)?
**TDD (Разработка через тестирование)** — это подход к программированию, при котором **тесты пишутся ДО написания самого рабочего кода**.

Процесс строится по повторяющемуся циклу **Red - Green - Refactor**:
1. **Красный этап (Red)**:
   Пишется unit-тест на метод, которого еще нет в программе. Тест запускается и гарантированно падает с ошибкой (горит красным).
2. **Зеленый этап (Green)**:
   Пишется самый простой и минимальный рабочий код, достаточный только для того, чтобы тест прошел успешно (загорелся зеленым).
3. **Этап рефакторинга (Refactor)**:
   Написанный код чистится от дублирования, оптимизируется и форматируется. Тест запускается снова: если он все еще зеленый, задача выполнена.

## Тема 5. Модульные (Unit) тесты против Интеграционных тестов

| Свойство | Модульные (Unit) тесты | Интеграционные тесты |
| :--- | :--- | :--- |
| **Что тестируют** | Один класс или метод изолированно от внешнего мира. | Взаимодействие нескольких классов, Spring-контекста и СУБД. |
| **Внешние зависимости (БД, сеть)** | Подменяются фальшивыми объектами (**Моками**). | Используют реальную тестовую БД (PostgreSQL, Testcontainers, H2). |
| **Скорость выполнения** | **Мгновенно** (десятки миллисекунд на класс). Все 65 тестов сервисов выполняются за 5 секунд. | **Медленно** (требуется время на старт Spring Boot и накат миграций БД). |
| **Локализация ошибки** | Если тест упал — ошибка ровно в тех 5 строках метода, который тестируется. | Если тест упал — ошибка может быть в логике, в SQL-запросе, в сети или в схеме таблиц. |
| **Пример в нашем проекте** | Классы `RecipeServiceUnitTest`, `UserServiceTest` и др. | Класс `RecipePlatformApplicationTests` со свойствами `@SpringBootTest`. |

## Тема 6. Инструменты тестирования: JUnit 5 и Mockito

### Что такое JUnit 5?
**JUnit 5** — это главный фреймворк для написания и запуска тестов в экосистеме Java.
- `@Test` — помечает метод как тестовый сценарий.
- `@BeforeEach` — выполняется перед каждым тестом (используется для инициализации чистых объектов).
- `@DisplayName` — задает понятное текстовое описание теста на русском или английском языке.
- Утверждения (**Assertions**): методы `assertThat(...).isEqualTo(...)` из библиотеки **AssertJ**, проверяющие совпадение ожидаемого результата с фактическим.

---

### Что такое Mockito?
**Mockito** — это библиотека для создания фиктивных объектов-заглушек (**Mock-объектов**).

Когда мы тестируем `UserService`, нам не нужна настоящая база данных. Мы заменяем интерфейс `UserRepository` мок-объектом:
```java
@Mock
private UserRepository userRepository;
```

#### Ключевые механизмы Mockito:
1. **Стаббинг (Stubbing / Задание поведения)**:
   Обучаем мок, что отвечать при определенных вызовах:
   ```java
   when(userRepository.findById(1L)).thenReturn(Optional.of(user));
   ```
   Или указание выбросить исключение:
   ```java
   when(userRepository.findById(999L)).thenReturn(Optional.empty());
   ```
2. **Верификация (Verification / Проверка вызовов)**:
   Проверяем, вызывался ли метод у мока:
   ```java
   verify(userRepository).delete(user); // проверяет, что метод delete был вызван 1 раз
   verify(userRepository, never()).save(any()); // проверяет, что метод save НЕ вызывался
   ```
3. **Перехват аргументов (ArgumentCaptor)**:
   Позволяет поймать объект, который сервис передал в метод репозитория, чтобы проверить его внутренние поля:
   ```java
   ArgumentCaptor<Recipe> captor = ArgumentCaptor.forClass(Recipe.class);
   verify(recipeRepository).save(captor.capture());
   assertThat(captor.getValue().getTitle()).isEqualTo("Борщ");
   ```

## Блок: Вопросы и ловушки преподавателя с готовыми ответами

### Вопрос 1: Зачем в методе `createBulk` сервиса `RecipeService` стоит вызов `recipeRepository.saveAndFlush(...)`, а не обычный `save(...)`?
**Ответ:**
Метод `save(...)` в Spring Data JPA просто прикрепляет сущность к контексту персистентности Hibernate и может отложить реальную отправку SQL-запроса `INSERT` до самого закрытия транзакции.
Метод `saveAndFlush(...)` принудительно сразу же сбрасывает изменения в базу данных. Это принципиально для неатомарного метода `createBulkWithoutTransaction`: каждый объект сохраняется и фиксируется в БД немедленно, поэтому при падении следующего рецепта предыдущий уже гарантированно остался в таблице.

---

### Вопрос 2: Являются ли промежуточные операции стрима (`map`, `filter`) жадными (eager) или ленивыми (lazy)? Что это значит на практике?
**Ответ:**
Все промежуточные операции в Stream API являются **ленивыми (lazy)**.
Это означает, что при вызове `dtos.stream().map(...)` никакой фактической обработки данных еще не происходит. Промежуточные операции лишь строят план конвейера. Обработка начнется только тогда, когда будет вызвана терминальная операция (например, `.toList()` или `.collect()`). Если терминальную операцию не вызвать, стрим не выполнит ни одной строчки кода внутри лямбд.

---

### Вопрос 3: Почему вызов `optional.get()` считается плохой практикой (code smell)?
**Ответ:**
Если объект `Optional` окажется пустым, прямой вызов `.get()` выбросит исключение `NoSuchElementException`. Это ничем не лучше старого `NullPointerException`. Правильный подход — использовать безопасные методы, которые явно указывают поведение при отсутствии значения: `.orElse(...)`, `.orElseGet(...)` или `.orElseThrow(...)`.

---

### Вопрос 4: Чем mock отличается от spy в Mockito?
**Ответ:**
- **Mock (Заглушка)**: полностью фиктивный объект. Все его методы по умолчанию возвращают значения-пустышки (`null`, `0`, `false`, пустые коллекции), если мы явно не настроили их через `when(...)`.
- **Spy (Шпион)**: оборачивает **реальный** существующий экземпляр объекта. Если метод шпиона не был переопределен через `when(...)`, он выполнит свой настоящий рабочий код.

---

### Вопрос 5: Зачем нам нужны unit-тесты на Mockito, если у нас уже есть интеграционные тесты с базой данных?
**Ответ:**
1. **Скорость**: Интеграционные тесты требуют запуска контекста Spring и инициализации базы данных (секунды или минуты при росте проекта). Все наши 65 unit-тестов выполняются за 5 секунд.
2. **Изоляция и чистота**: Интеграционные тесты зависят от состояния БД и порядка выполнения. Unit-тесты проверяют чистую алгоритмическую логику класса без риска внешних сетевых или аппаратных сбоев.
3. **Покрытие граничных условий**: В unit-тестах с Mockito легко сымитировать редкие сбои (например, выброс специфического исключения базой данных), которые сложно воспроизвести в живой БД.
