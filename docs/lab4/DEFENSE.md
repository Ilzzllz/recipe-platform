## Тема 1. Исключения в Java: Проверяемые (Checked) и Непроверяемые (Unchecked)

### Иерархия классов исключений в Java

Все ошибки и исключительные ситуации в Java являются объектами. Во главе иерархии стоит класс `java.lang.Throwable`.

От `Throwable` отходят две главные ветви:
1. `java.lang.Error` — критические системные сбои на уровне виртуальной машины Java (JVM), которые программа не может и не должна обрабатывать (например, `OutOfMemoryError` — закончилась оперативная память, `StackOverflowError` — переполнение стека вызовов при бесконечной рекурсии).
2. `java.lang.Exception` — исключительные ситуации, возникающие во время работы программы, которые программа может перехватить и обработать.

Внутри `Exception` существует разделение:
- **Непроверяемые исключения (Unchecked Exceptions)**: класс `RuntimeException` и все его наследники (например, `NullPointerException`, `IllegalArgumentException`, `IndexOutOfBoundsException`).
- **Проверяемые исключения (Checked Exceptions)**: сам класс `Exception` и все его прямые наследники, кроме `RuntimeException` (например, `IOException`, `SQLException`, `ClassNotFoundException`).

```
                    java.lang.Throwable
                       /          \
                      /            \
        java.lang.Error        java.lang.Exception
                                   /          \
                                  /            \
                Checked Exceptions      java.lang.RuntimeException
             (IOException, SQLException)    (Unchecked Exceptions)
                                            (NullPointerException, 
                                             IllegalArgumentException,
                                             наш NotFoundException)
```

---

### Главные различия между Checked и Unchecked

| Критерий | Checked (Проверяемые) | Unchecked (Непроверяемые) |
| :--- | :--- | :--- |
| **Базовый класс** | Наследуются от `Exception` (но не от `RuntimeException`). | Наследуются от `RuntimeException`. |
| **Контроль компилятором** | **Обязателен**. Компилятор Java откажется компилировать код, если метод не перехватил такое исключение (`try-catch`) или не объявил его в сигнатуре через `throws`. | **Не обязателен**. Метод не обязан оборачивать вызов в `try-catch` и не обязан писать `throws`. |
| **Смысл и назначение** | Предсказуемые внешние ситуации, на которые программа может отреагировать и восстановиться (например, файл не найден на диске, сервер разорвал сетевое соединение). | Ошибки программиста в логике программы или критические нарушения контракта вызова (передан `null`, индекс за границами массива, деление на ноль, сущность не найдена по ID). |

---

### Почему современный Spring отдает предпочтение Unchecked Exceptions?

1. **Отсутствие загромождения кода (Pollution)**: Если бы сервисный слой выбрасывал checked-исключения, каждый метод по цепочке `Repository -> Service -> Controller` был бы вынужден прописывать `throws MyException` в своей сигнатуре.
2. **Чистота интерфейсов**: Интерфейсы стандартных библиотек (например, Java Stream API или функциональные интерфейсы `Consumer`, `Function`, `Supplier`) не могут принимать методы, выбрасывающие checked-исключения, без дополнительных оберток.
3. **Глобальная обработка**: В Spring принят подход централизованной обработки: сервисы просто выбрасывают unchecked-исключения (`NotFoundException extends RuntimeException`), а фреймворк на уровне `@ControllerAdvice` ловит их автоматически, не требуя ручных проверок на промежуточных слоях.

### Как это реализовано в нашем проекте:
Класс [`NotFoundException`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/exception/NotFoundException.java) унаследован от `RuntimeException`:
```java
public class NotFoundException extends RuntimeException {
    public NotFoundException(String message) {
        super(message);
    }
}
```
Благодаря этому методы сервисов (например, `RecipeService.getById`) не загромождают сигнатуры операторами `throws`, а исключение поднимается сразу в `GlobalExceptionHandler`.

## Тема 2. Архитектура обработки ошибок в Spring: `@ControllerAdvice`, `@ExceptionHandler`, `@Valid`

### 1. Что такое `@ControllerAdvice` и `@RestControllerAdvice`?

- `@ControllerAdvice` — это специализированная аннотация Spring (стереотип), которая превращает класс в глобальный перехватчик событий контроллеров.
- Это реализация паттерна **Interceptor (Перехватчик)**. Spring MVC применяет логику этого класса ко всем контроллерам приложения.
- **Разница между `@ControllerAdvice` и `@RestControllerAdvice`**:
  - `@ControllerAdvice` предназначен для классических MVC-контроллеров, которые возвращают имена HTML-шаблонов (View).
  - `@RestControllerAdvice` — это комбинация аннотаций `@ControllerAdvice` и `@ResponseBody`. Она указывает, что возвращаемые методами объекты должны автоматически сериализоваться в тело HTTP-ответа (по умолчанию в формат JSON через библиотеку Jackson).
  - В нашем проекте используется именно `@RestControllerAdvice` в классе [`GlobalExceptionHandler.java`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/exception/GlobalExceptionHandler.java).

---

### 2. Как работает аннотация `@ExceptionHandler`?

Внутри класса `@RestControllerAdvice` методы помечаются аннотацией `@ExceptionHandler(ИмяКлассаИсключения.class)`.

**Алгоритм работы Spring MVC при возникновении ошибки:**
1. Клиент делает HTTP-запрос (например, `GET /api/recipes/999`).
2. В методе контроллера или сервиса выбрасывается исключение (например, `NotFoundException`).
3. Запрос прерывается, и управление переходит к системному компоненту Spring MVC — `HandlerExceptionResolverComposite`.
4. Spring ищет среди всех бинов с аннотацией `@ControllerAdvice` метод с аннотацией `@ExceptionHandler`, тип которого соответствует выброшенному исключению.
5. **Правило выбора обработчика (Самый специфичный класс)**: Если для ошибки `NotFoundException` есть отдельный метод `@ExceptionHandler(NotFoundException.class)` и общий метод `@ExceptionHandler(Exception.class)`, Spring всегда выберет метод, чей тип класса находится ближе всего по дереву наследования к выброшенному исключению (то есть `NotFoundException`).
6. Метод-обработчик формирует объект `ApiError` и возвращает `ResponseEntity` с нужным HTTP-статусом (например, 404).
7. Spring преобразует `ApiError` в JSON и отправляет клиенту.

---

### 3. Как работает валидация входных данных через `@Valid`?

Валидация в Spring строится на базе спецификации **Jakarta Bean Validation** (JSR 380), эталонной реализацией которой является **Hibernate Validator**.

**Как это работает шаг за шагом:**
1. В классах DTO поля размечаются аннотациями ограничений:
   - `@NotNull` — значение поля не должно быть `null`.
   - `@NotEmpty` — значение не `null`, и длина строки (или размер коллекции) больше 0.
   - `@NotBlank` — значение не `null`, длина больше 0, и строка содержит хотя бы один непробельный символ.
   - `@Email` — строка должна соответствовать формату адреса электронной почты.
2. В контроллере перед аргументом метода ставится аннотация `@Valid`:
   ```java
   @PostMapping
   public UserDto create(@Valid @RequestBody UserCreateDto dto)
   ```
3. Перед тем как вызвать метод контроллера, Spring считывает входящий JSON, превращает его в объект Java (`UserCreateDto`) и запускает валидатор `Validator.validate(dto)`.
4. Если хотя бы одно поле нарушает правила:
   - Метод контроллера **вообще не вызывается**.
   - Spring выбрасывает исключение `MethodArgumentNotValidException`.
   - Внутри этого исключения содержится объект `BindingResult`, в котором записан список всех полей и сообщений об ошибках.
5. В нашем классе `GlobalExceptionHandler` метод `handleMethodArgumentNotValid` достает все ошибки из `BindingResult` и упаковывает их в поле `details.fieldErrors`:
   ```java
   Map<String, Object> details = new LinkedHashMap<>();
   details.put("fieldErrors", exception.getBindingResult()
           .getFieldErrors()
           .stream()
           .collect(Collectors.toMap(
                   FieldError::getField,
                   FieldError::getDefaultMessage,
                   (first, second) -> first,
                   LinkedHashMap::new
           )));
   ```

## Тема 3. Логирование в Java и Spring Boot: Logback, уровни и ротация

### 1. Зачем нужно логирование вместо `System.out.println`?

1. **Производительность**: `System.out.println` выполняет синхронную блокирующую запись в стандартный вывод операционной системы. Это тормозит все потоки приложения. Логирующие фреймворки умеют писать асинхронно через буфер.
2. **Уровни важности**: Вывод в консоль нельзя быстро выключить без изменения кода. Логирование позволяет одной строчкой в конфигурации скрыть подробные отладочные сообщения в продакшене.
3. **Место назначения**: `System.out.println` выводит только в терминал. Библиотеки логирования умеют параллельно писать в консоль, в файлы на диске, отправлять по сети в системы сбора логов (Elasticsearch, Graylog).
4. **Контекст и метаданные**: Логгер автоматически добавляет к каждому сообщению дату, точное время до миллисекунд, имя потока, класс и уровень важности.

---

### 2. Связка SLF4J и Logback (Фасад и Реализация)

- **SLF4J (Simple Logging Facade for Java)** — это **интерфейс (фасад)**. Он предоставляет набор интерфейсов (`Logger`, `LoggerFactory`), через которые программист пишет в коде:
  ```java
  private static final Logger logger = LoggerFactory.getLogger(MyClass.class);
  logger.info("Some message: {}", value);
  ```
  Код приложения зависит только от интерфейса SLF4J и ничего не знает о конкретной библиотеке записи логов.
- **Logback** — это **реализация** логгера (движок), которая непосредственно форматирует строки и записывает их на диск или в консоль.
- В Spring Boot библиотека Logback используется по умолчанию "из коробки" через стартер `spring-boot-starter-logging`.

---

### 3. Уровни логирования

Уровни логирования выстроены в строгую иерархию (от самого подробного к самому критическому):

1. **TRACE** — сверхподробные шаги алгоритма (вход в цикл, значения локальных переменных).
2. **DEBUG** — полезная отладочная информация для разработчиков при поиске багов (какие параметры пришли в метод, состояние объекта).
3. **INFO** — информационные события штатной работы системы (старт сервиса, успешное создание записи, входящий запрос).
4. **WARN** — предупреждения о потенциальных проблемах, которые не сломали программу, но требуют внимания (ресурс не найден по ID, повторная попытка соединения, слишком медленный ответ).
5. **ERROR** — серьезные сбои и ошибки, прервавшие выполнение операции (упало непредвиденное исключение, недоступна база данных).

**Правило фильтрации**: Если для логгера установлен уровень `INFO`, система будет записывать сообщения уровней `INFO`, `WARN` и `ERROR`, а сообщения уровней `TRACE` и `DEBUG` будут проигнорированы.

---

### 4. Ротация логов

**Что такое ротация логов?**
Это процесс автоматического закрытия текущего файла логов, переноса его в архив (с переименованием или сжатием) и создания нового чистого файла для продолжения записи.

**Зачем нужна ротация?**
Если приложение работает годами, один файл логов может вырасти до десятков или сотен гигабайт. Это приведет к:
- Полному заполнению свободного места на жестком диске (сервер перестанет работать).
- Невозможности открыть файл текстовым редактором для анализа инцидента.

**Как настроена ротация в нашем проекте ([`logback-spring.xml`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/resources/logback-spring.xml)):**
- Используется комбинированная политика `SizeAndTimeBasedRollingPolicy`:
  - **По времени**: каждый новый день текущий файл переименовывается с добавлением даты `recipe-platform-%d{yyyy-MM-dd}.%i.log`.
  - **По размеру**: если в течение текущего дня объем файла превысил `10MB`, он архивируется с инкрементом индекса `%i` (например, `recipe-platform-2026-09-12.0.log`, `recipe-platform-2026-09-12.1.log`).
  - **По сроку хранения**: `<maxHistory>30</maxHistory>` — логи хранятся 30 дней, файлы старше 30 дней автоматически удаляются.
  - **По общему объему**: `<totalSizeCap>1GB</totalSizeCap>` — общий размер всех сохраненных файлов архива не превысит 1 гигабайт.

## Тема 4. Аспектно-ориентированное программирование (AOP)

### Основная концепция AOP

В любой программе есть два типа задач:
1. **Основная бизнес-логика (Core Concerns)**: вычисление стоимости заказа, создание пользователя, сохранение рецепта в базу данных.
2. **Сквозная функциональность (Cross-Cutting Concerns)**: задачи, которые не имеют прямого отношения к бизнесу, но нужны по всей системе:
   - Логирование вызовов и времени работы;
   - Проверка прав доступа (Security);
   - Управление транзакциями (`@Transactional`);
   - Кеширование данных (`@Cacheable`).

Если писать код сквозных задач внутри каждого бизнес-метода, бизнес-логика утонет в дублирующемся коде (нарушение принципа DRY).
**Аспектно-ориентированное программирование (АОП)** позволяет вынести сквозную логику в отдельные модули — **Аспекты**, которые автоматически "оборачивают" нужные бизнес-методы.

---

### Ключевые термины AOP

1. **Aspect (Аспект)**: Модуль (класс), объединяющий в себе сквозную логику. В нашем коде это класс [`LoggingAspect.java`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/aspect/LoggingAspect.java), помеченный аннотацией `@Aspect`.
2. **JoinPoint (Точка соединения)**: Момент во время выполнения программы, где к коду может быть применен аспект. В Spring AOP точкой соединения всегда является **вызов метода Spring-бина**.
3. **Pointcut (Срез точек соединения)**: Предикат (выражение), который отбирает, к каким именно методам нужно применить аспект. В нашем проекте это:
   ```java
   @Around("execution(* com.example.recipeplatform.service.*.*(..))")
   ```
   Разбор этого выражения:
   - `execution` — перехват выполнения метода;
   - первый `*` — любой тип возвращаемого значения (`void`, `RecipeDto`, `List` и т.д.);
   - `com.example.recipeplatform.service.*` — любой класс внутри пакета сервисов;
   - второй `*` — любое имя метода;
   - `(..)` — любые параметры метода (ноль или больше, любых типов).
4. **Advice (Совет)**: Код, который выполняется в точке соединения. Виды советов:
   - `@Before` — выполняется перед целевым методом;
   - `@After` — выполняется после завершения целевого метода (даже если упала ошибка);
   - `@AfterReturning` — выполняется только после успешного возврата из метода;
   - `@AfterThrowing` — выполняется, если метод выбросил исключение;
   - `@Around` — самый мощный совет: полностью оборачивает вызов метода (до вызова, сам вызов и после вызова). Позволяет измерить время или изменить возвращаемое значение.
5. **Weaving (Внедрение / Связывание)**: Процесс соединения аспектов с целевыми объектами. В Spring AOP внедрение происходит **динамически во время выполнения (Runtime Weaving)** с помощью создания прокси-объектов.

---

### Как Spring реализует AOP под капотом (Паттерн Proxy)

Когда Spring видит класс, к которому применен аспект (например, `RecipeService`), он создает в контексте не сам объект `RecipeService`, а специальную динамическую обертку — **Proxy (Заместитель)**.

- Когда контроллер вызывает `recipeService.findAll()`, вызов на самом деле приходит в метод Proxy-объекта.
- Прокси запускает код метода `@Around` аспекта `LoggingAspect`.
- Внутри аспекта вызов `joinPoint.proceed()` передает управление настоящему объекту `RecipeService`.
- После возврата из настоящего метода прокси возвращает результат контроллеру.

## Тема 5. Логирование через AOP против логирования в коде методов

| Критерий | Логирование через AOP | Логирование внутри кода метода |
| :--- | :--- | :--- |
| **Где находится код** | В одном централизованном классе-аспекте. | Разбросан по телам сотен методов в сервисах. |
| **Принцип DRY** | Полное соблюдение: логика замера пишется 1 раз. | Нарушение: строчки `System.nanoTime()` копируются везде. |
| **Доступ к контексту** | Имеет доступ только к входным аргументам, имени метода и результату возврата. | Имеет доступ ко всем локальным переменным внутри метода. |
| **Какую информацию логирует** | Системные и инфраструктурные метрики: время выполнения, имя метода, факт возникновения исключения. | Специфические бизнес-шаги: "пользователь подтвердил телефон", "начался пересчет скидки для товара X". |

**Золотое правило промышленной разработки**:
- Метрики времени, аудит вызовов и мониторинг ошибок реализуются **через AOP**.
- Логирование конкретных бизнес-решений и промежуточных состояний внутри сложного алгоритма делается **напрямую в коде метода**.

## Тема 6. Паттерны проектирования (GoF Patterns)

Классификация "Банды Четырех" (GoF — Gang of Four) делит паттерны на 3 категории:
1. **Порождающие (Creational)** — отвечают за удобное и безопасное создание объектов.
2. **Структурные (Structural)** — отвечают за построение удобных связей и композиции классов.
3. **Поведенческие (Behavioral)** — отвечают за эффективное распределение обязанностей и взаимодействие между объектами.

Ниже приведен подробный разбор ключевых паттернов с указанием, где они работают в нашем проекте.

---

### 1. Порождающие паттерны

#### Singleton (Одиночка) — Обязательный для защиты
- **Суть паттерна**: Гарантирует, что у класса есть только один экземпляр, и предоставляет глобальную точку доступа к нему.
- **В классической Java**: Реализуется через приватный конструктор и статическое поле с методом `getInstance()` (например, с двойной проверкой блокировки `Double-Checked Locking` для потокобезопасности).
- **В Spring Framework**: По умолчанию все создаваемые бины (`@Component`, `@Service`, `@Repository`, `@RestControllerAdvice`) имеют область видимости **Singleton (Scope: singleton)**. Spring контейнер создает ровно один экземпляр каждого сервиса (`RecipeService`, `LoggingAspect`, `GlobalExceptionHandler`) при старте приложения и внедряет одну и ту же ссылку во все зависимые контроллеры.

#### Factory Method / Builder (Строитель)
- **Суть Builder**: Позволяет пошагово конструировать сложные объекты, избегая "телескопических" конструкторов с десятком параметров.
- **В нашем коде**: Метод создания HTTP-ответов `ResponseEntity.status(HttpStatus.NOT_FOUND).body(error)` использует паттерн Builder.

---

### 2. Структурные паттерны

#### Proxy (Заместитель)
- **Суть паттерна**: Объект-заместитель перехватывает обращения к оригинальному объекту и позволяет выполнить дополнительную работу до или после передачи вызова оригиналу.
- **В нашем коде**: На паттерне Proxy полностью построен весь Spring AOP. Наш класс `LoggingAspect` перехватывает вызовы методов сервисов именно через прокси-обертку, которую генерирует Spring. На этом же паттерне работает декларативное управление транзакциями `@Transactional`.

#### Adapter (Адаптер)
- **Суть паттерна**: Преобразует интерфейс одного класса в интерфейс, ожидаемый клиентом, позволяя работать вместе классам с несовместимыми интерфейсами.
- **В нашем коде**: Все наши классы-мапперы ([`RecipeMapper`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/mapper/RecipeMapper.java), `UserMapper`, `CategoryMapper`) являются классическими адаптерами: они адаптируют внутренние JPA-сущности (`Recipe`, `User`) к формату внешних DTO-объектов (`RecipeDto`, `UserDto`), скрывая служебные поля базы данных.

---

### 3. Поведенческие паттерны

#### Strategy (Стратегия)
- **Суть паттерна**: Определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми.
- **В нашем коде**: В Spring MVC выбор механизма валидации, сериализации JSON или обработки ошибок строится на паттерне Стратегия. Например, `HandlerExceptionResolver` — это стратегия обработки возникших ошибок, а разные реализации этой стратегии обрабатывают разные типы сбоев.

#### Chain of Responsibility (Цепочка обязанностей)
- **Суть паттерна**: Передает запрос последовательно по цепочке обработчиков, пока один из них не обработает запрос.
- **В веб-приложении Spring**: Запрос клиента проходит через цепочку сервлетных фильтров (`Filter Chain`) перед тем, как попасть в `DispatcherServlet`.

## Тема 7. Рефакторинг программного кода

### Что такое рефакторинг?
**Рефакторинг** — это процесс изменения внутренней структуры программы, который:
1. Не меняет ее внешнего поведения (с точки зрения клиента API работает точно так же).
2. Делает код более чистым, понятным, тестируемым и легким для сопровождения.

### Признаки плохого кода (Code Smells — "Код с душком")
1. **Дублирование кода (Duplicated Code)** — одинаковые фрагменты кода скопированы в нескольких местах.
2. **Длинный метод (Long Method)** — метод содержит более 25-30 строк и выполняет слишком много действий.
3. **Большой класс / Божественный объект (God Object)** — класс берет на себя слишком много несвязанных обязанностей.
4. **Длинный список параметров (Long Parameter List)** — метод принимает 5-10 отдельных переменных вместо одного объекта-структуры.

### Какие приемы рефакторинга применены в нашей лабораторной:
1. **Внедрение DTO (Introduce Parameter Object)**:
   - *Было*: В контроллеры могли передаваться разрозненные строки и числа.
   - *Стало*: Введены объекты передачи данных (`RecipeCreateDto`, `UserCreateDto`).
2. **Вынесение обработки ошибок (Centralized Exception Handling)**:
   - *Было*: В каждом методе контроллера мог стоять блок `try-catch` с ручным формированием `Map<String, String>` для ответа об ошибке.
   - *Стало*: Вся обработка исключений вынесена в один класс [`GlobalExceptionHandler`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/exception/GlobalExceptionHandler.java).
3. **Вынесение сквозной логики через AOP (Extract Aspect)**:
   - *Было*: В начале каждого сервисного метода писали `long start = System.currentTimeMillis()`, а в конце — `System.out.println(System.currentTimeMillis() - start)`.
   - *Стало*: Создан один универсальный аспект [`LoggingAspect`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/aspect/LoggingAspect.java), а сервисный код остался на 100% чистым.

## Блок: Каверзные вопросы и ловушки преподавателя с готовыми ответами

### Вопрос 1: В чем разница между `@ControllerAdvice` и `@RestControllerAdvice`?
**Ответ:**
`@RestControllerAdvice` — это аннотация-композиция, включающая в себя `@ControllerAdvice` и `@ResponseBody`. Методы обычного `@ControllerAdvice` по умолчанию возвращают имена HTML-представлений (View), а методы `@RestControllerAdvice` автоматически сериализуют возвращаемый объект (в нашем случае `ApiError`) прямо в тело HTTP-ответа в формате JSON.

---

### Вопрос 2: Что делает метод `joinPoint.proceed()` в аспекте? Что будет, если мы забудем его вызвать?
**Ответ:**
Метод `joinPoint.proceed()` передает управление дальше по цепочке — либо следующему аспекту, либо самому целевому бизнес-методу сервиса, и возвращает результат его выполнения.
Если мы забудем вызвать `joinPoint.proceed()`, оригинальный метод сервиса **никогда не выполнится**. Контроллер получит `null` (или результат, который мы вернем из аспекта вручную), а сохранение данных или чтение из БД не произойдет.

---

### Вопрос 3: Почему в `LoggingAspect` блок расчета времени помещен именно в `finally`?
**Ответ:**
Потому что в целевом методе сервиса может произойти исключение (например, `NotFoundException`). Если бы расчет времени стоял после `proceed()`, при возникновении исключения управление сразу вылетело бы из метода, и мы не залогировали бы время выполнения аварийного вызова. Блок `finally` гарантирует выполнение замера и логирования всегда: как при успешном исходе, так и при падении с ошибкой.

---

### Вопрос 4: Почему для замера времени мы использовали совет `@Around`, а не пару `@Before` и `@After`?
**Ответ:**
Советы `@Before` и `@After` — это два изолированных метода. Они не имеют общей локальной области видимости для переменных. Чтобы передать метку времени `start` из `@Before` в `@After`, пришлось бы сохранять ее во внешнем хранилище (например, в `ThreadLocal`). Это усложняет код и чревато утечками памяти.
Совет `@Around` оборачивает весь жизненный цикл вызова в рамках одного метода: мы объявляем локальную переменную `start` прямо в стеке потока до вызова `proceed()` и используем ее в `finally`.

---

### Вопрос 5: Что произойдет, если один метод сервиса вызовет другой метод этого же самого сервиса (`self-invocation`)? Сработает ли AOP-логирование?
*(Это любимый вопрос преподавателей на засыпку!)*
**Ответ:**
**Логирование для второго метода НЕ сработает!**
Spring AOP работает через генерацию **Proxy-объекта**. Когда внешний контроллер вызывает сервис, он обращается к Proxy, и аспект срабатывает. Но когда метод внутри сервиса вызывает `this.anotherMethod()`, вызов идет напрямую внутри реального экземпляра класса через ссылку `this`, минуя Proxy-объект. Поэтому перехвата не происходит.

---

### Вопрос 6: Чем принципиально отличаются аннотации валидации `@NotNull`, `@NotEmpty` и `@NotBlank`?
**Ответ:**
- `@NotNull`: проверяет только, что ссылка `!= null`. Но значение `""` (пустая строка) или `"   "` (пробелы) пройдет проверку успешно.
- `@NotEmpty`: проверяет, что ссылка `!= null` и ее длина `> 0`. Значение `""` не пройдет, но строка из одних пробелов `"   "` пройдет проверку.
- `@NotBlank`: самая строгая проверка для строк. Проверяет, что строка `!= null`, не пустая и после удаления пробелов по краям (`trim()`) содержит хотя бы один непробельный символ.

---

### Вопрос 7: Если в DTO есть вложенный объект или список (например, список шагов рецепта `List<RecipeStepCreateDto> steps`), будет ли выполнена валидация внутренних полей шага, если над списком стоит только `@NotEmpty`?
**Ответ:**
**Нет, не будет.**
Аннотация `@NotEmpty` проверит только то, что сам список не пустой (в нем есть хотя бы один элемент). Чтобы валидатор заглянул внутрь каждого объекта списка и проверил его собственные поля (`stepOrder`, `description`), над полем списка обязательно должна стоять аннотация `@Valid`. Это называется **каскадной валидацией (Cascaded validation)**. В нашем `RecipeCreateDto` стоит именно связка `@Valid @NotEmpty`.

---

### Вопрос 8: Чем отличается Singleton в Spring от классического Singleton из книги GoF?
**Ответ:**
- **Классический GoF Singleton**: жестко гарантирует наличие одного экземпляра на уровне всего загрузчика классов (ClassLoader) виртуальной машины Java за счет статической переменной и приватного конструктора.
- **Spring Singleton**: гарантирует наличие одного экземпляра на уровне одного **Spring ApplicationContext** (контейнера внедрения зависимостей). Сам класс при этом имеет обычный публичный конструктор, и если создать его через `new MyService()`, Java создаст новый отдельный объект.

### Вопрос 9: Где хранятся логи при закрытии приложения, и что с ними происходит через 30 дней?
**Ответ:**
Логи записываются в директорию `logs/` в корне проекта в файл `recipe-platform.log`. В соответствии с настроенной в `logback-spring.xml` политикой `SizeAndTimeBasedRollingPolicy`, архивные файлы сжимаются и именуются по датам. Через 30 дней (параметр `<maxHistory>30</maxHistory>`) фоновый процесс Logback автоматически удаляет файлы логов, созданные более месяца назад, освобождая дисковое пространство.

### Вопрос 10: Что такое OpenAPI и Swagger? В чем разница между ними?
**Ответ:**
- **OpenAPI** — это **спецификация (стандарт)** машиночитаемого описания REST API в формате JSON или YAML (описывает пути, DTO, статус-коды).
- **Swagger** — это **набор инструментов**, созданных для работы с этой спецификацией. Например, **Swagger UI** — это веб-интерфейс, который считывает спецификацию OpenAPI и отображает красивую интерактивную веб-страницу с кнопками "Try it out" для отправки живых запросов.

### Вопрос 11 (Ловушка преподавателя по логированию ошибок):
> *«Как у вас настроено логирование ошибок в `GlobalExceptionHandler`? Виден ли в логах код ошибки (например, 500 или 404), и почему в логах не должно быть длинных стектрейсов (stack trace)?»*

**Ответ:**
1. **Код ошибки явно пишется в лог**:
   В [`GlobalExceptionHandler.java`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/java/com/example/recipeplatform/exception/GlobalExceptionHandler.java) каждый обработчик формирует структурированное сообщение с обязательным указанием HTTP статус-кода, HTTP-метода и URI эндпоинта:
   - При 500: `logger.error("HTTP 500 [INTERNAL_SERVER_ERROR] on {} {}: {} (Exception: {})", ...)`
   - При 404: `logger.warn("HTTP 404 [NOT_FOUND] on {} {}: {}", ...)`
   - При 400: `logger.warn("HTTP 400 [BAD_REQUEST] on {} {}: {}", ...)`
   - При 409: `logger.error("HTTP 409 [CONFLICT] on {} {}: {}", ...)`
2. **Стектрейсы исключены из логов по двум ключевым причинам**:
   - **Информационный шум и переполнение диска**: Обычный Java-стектрейс занимает от 50 до 150 строк служебного вызова библиотек Spring, Tomcat и Hibernate. Под высокой нагрузкой логи мгновенно забьют диск и сделают чтение логов человеком или парсерами (ELK/Logstash) нечитаемым месивом.
   - **Безопасность (Security)**: Стектрейсы раскрывают внутреннее устройство системы (пути к файлам, версии библиотек, имена внутренних методов), что при утечке логов облегчает злоумышленникам эксплуатацию уязвимостей.
3. **Как это технически гарантировано в нашем проекте**:
   - **На уровне Java-кода**: В вызовы `logger.error(...)` и `logger.warn(...)` передаются только отформатированные строки и параметры сообщения. Мы намеренно **не передаем** объект исключения `exception` последним параметром, так как именно передача объекта `Throwable` заставляет SLF4J/Logback печатать весь стек-трейс.
   - **На уровне конфигурации Logback**: В шаблоне логирования [`logback-spring.xml`](file:///C:/Users/Formatis/Documents/GitHub/recipe-platform/src/main/resources/logback-spring.xml) добавлен конвертер `%nopex`, который подавляет автоматический вывод стектрейсов даже в случае системных сбоев внешних библиотек.
